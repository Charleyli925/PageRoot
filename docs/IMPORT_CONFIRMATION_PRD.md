# 外部 HTML 打开、导入确认与项目归属

- 文档版本：PRD v1.1
- 最近更新：2026-08-16（Asia/Shanghai，UTC+8）
- 状态：产品规则已确认；现有 [修改计划](IMPORT_CONFIRMATION_PLAN.md) 的“再次打开原稿”条款已被本文取代，实施前必须先同步计划
- 适用范围：桌面版打开本地 `.html` / `.htm`，包括首次打开外部文件、再次打开已导入原文件、直接打开已登记 PageRoot 项目文件
- 关联文档：[版本与项目文件产品需求](VERSION_AND_PROJECT_FILES_PRD.md)、[MVP 产品需求](MVP_PRD.md)、[交互流程](INTERACTION_FLOW.md)、[状态所有权](STATE_OWNERSHIP.md)、[安全模型](SECURITY_MODEL.md)、[ADR 0022](decisions/0022-user-owned-project-root-identity.md)

本文统一规定一份本地 HTML 从“外部原文件”进入 PageRoot、再次从外部打开、回到已有项目以及查看初始版本 V1 的完整产品逻辑。

它修正两类不能分开处理的问题：

1. 首次打开未登记 HTML 时，现行产品会直接复制、改名并切换到项目文件，用户不清楚文件去了哪里。
2. 原文件被保留后，用户再次打开同一份原文件，现行 Repository 只把项目根内已登记文件识别为项目文件；外部原路径只参与导入重试，不能在项目已经编辑或晋升后稳定找回原项目，因此可能再次导入、重复建项目，并让打开/画布确认状态落入不必要的复杂分支。

这不是只有高频测试才会遇到的特殊情况。任何保留下载目录、桌面或业务文件夹中原稿，并习惯从 Finder 再次双击它的普通用户都可能遇到。产品必须把“外部源与 PageRoot 项目的长期归属”建模为正式事实，而不是把每次外部打开都当成一次全新导入。

版本、Working Copy、Candidate 和 Promotion 的基础语义仍以 [VERSION_AND_PROJECT_FILES_PRD](VERSION_AND_PROJECT_FILES_PRD.md) 为准。本文只补齐外部源关联和打开分流，不改变正式版本的生成规则。

## 1. 产品结论

> 首次打开一份尚未关联 PageRoot 项目的外部 HTML 时，先确认再导入；再次打开同一外部原文件时，不再导入，也不创建第二个项目，而是提示该文件已经关联项目，并让用户继续当前项目或查看初始版本 V1。

必须同时成立：

1. 有效 v4 Project 的已登记文件直接打开，不出现导入确认。
2. 真正全新的外部 HTML 先出现“首次导入确认”。用户确认后，PageRoot 原子地建立一个新项目、一个不可变初始版本 V1、一个可见 `…-V1.html` 和一条持久的外部源关联。
3. 同一外部源最多绑定一个 `projectId`。再次打开它时默认回到这个项目，绝不再次执行 `importExternal`。
4. 再次打开时，主操作是“继续当前项目”，目标是项目当前可编辑的本地工作稿；不能把它含混地写成“打开最新版本”。
5. 用户可以选择“查看初始版本 V1”。这里的 V1 是首次导入字节的不可变正式版本，只读打开；用户之后可以按既有历史版本流程选择“基于此版本继续编辑”。
6. 外部原文件、不可变 V1、可见 `…-V1.html` 和内部 Working Copy 是四个不同概念，见 §2。用户的本地修改只自动保存到项目内当前可见工作文件，不回写外部原稿，也不改写不可变 V1。
7. 首次导入默认保留外部原稿。只有用户明确勾选“成功导入后删除原文件”，才在项目完整发布后把刚才选中的 HTML 移入废纸篓。
8. 所有打开请求必须到达成功、取消或明确失败中的一个终态；“正在确认当前画布…”不能无限停留。

## 2. 文件、版本与本地编辑到底是什么关系

### 2.1 四个必须分开的对象

假设用户首次选择外部文件 `/桌面/A.html`，导入后项目内出现 `A-V1.html`：

| 对象 | 用户是否看得见 | 初始内容 | 后续本地修改 | 是否正式版本 |
|---|---|---|---|---|
| 外部原文件 `/桌面/A.html` | 是 | 用户选择时的原始字节 | PageRoot 不自动回写；除非用户主动在别处修改它，否则保持原样 | 否 |
| 隐藏的 V1 版本快照 | 默认不可见 | 与首次导入时所选文件逐字节一致 | 永远不变 | 是，正式版本 1 |
| 项目内可见工作文件 `A-V1.html` | 是 | 刚导入时与 V1 快照逐字节一致 | 用户编辑后自动保存到这里 | 否；它是基于 V1 的可编辑工作文件，不是不可变版本快照 |
| Working Copy | 不作为用户术语展示 | 从导入完成时就存在，记录 `A-V1.html` 当前编辑状态及其基于哪个正式版本 | 随本地保存更新 | 否，它是内部编辑状态，不是额外生成的一份 `A-working-copy.html` |

因此，不是“用户一修改 A，才出现一个 `A-working copy` 文件”。首次导入成功时，项目内可见 `A-V1.html` 及其内部 Working Copy 状态就已经存在。用户看到并编辑的是 `A-V1.html`；“Working Copy”只是系统内部用来表达“当前本地编辑基于哪个正式版本、是否与基线不同”的模型。

UI 不向普通用户展示“Working Copy”一词。对用户统一说“当前项目”“当前本地编辑”“已保存修改”或“基于版本 N”。

### 2.2 什么会自动保存，什么不会

用户在项目内的直接编辑、评论和附件按既有规则持久化。其中 HTML 修改自动保存到当前项目内可见工作文件，例如 `A-V1.html`。

以下对象不因本地保存而改变：

- 外部原文件 `/桌面/A.html`；
- 隐藏的不可变 V1 快照；
- 已存在的其他正式版本快照；
- 尚未被用户明确采纳的 AI Candidate。

即使用户连续本地保存 100 次，也仍然只有 V1；本地保存不是“发布 V2”。

### 2.3 什么时候才创建正式版本

正式版本只有两个入口：

1. 首次导入成功，创建正式版本 V1；
2. 用户明确采纳通过校验的 AI Candidate，创建下一个整数正式版本 V2、V3……

“发给 AI”、AI 返回候选、本地自动保存、评论变化和附件变化都不创建正式版本。

### 2.4 V1 与用户选择的文件是否一致

产品必须使用以下两层表述，不能混为一句：

1. 永远成立：**“初始版本 V1 与首次导入时所选文件一致。”**
2. 只有再次打开时读取当前外部原文件，且其 Hash 仍等于首次导入 Hash 才成立：**“当前这份原文件与项目初始版本 V1 完全一致。”**

外部原文件可能在首次导入后被用户用其他工具修改，所以“V1 与首次导入时的文件一致”不等于“V1 永远与外部路径当前内容一致”。当两者已经不同，界面必须明确说明原文件后来发生了变化，不能继续显示“完全一致”。

## 3. 统一的打开分类

每一条桌面打开请求在任何项目写入之前，必须被 Repository 分类为且只能分类为以下三类之一：

```text
用户选择或系统交付一份 HTML
  ├─ A. 已登记的有效 v4 项目文件 → 直接打开精确项目目标
  ├─ B. 已绑定的外部原文件       → 显示“已导入”关联确认
  └─ C. 真正全新的外部 HTML      → 显示“首次导入确认”
```

不存在面向用户的“这份源文件关联了多个项目，请选择一个”第四分支。Registry、导入事务和迁移门禁必须保证它不会成为正常产品状态，见 §4.5。

### 3.1 A 类：有效项目文件

以下情况按现有项目绑定和恢复直接打开，不出现本文两种确认框：

- 有效 v4 Working Copy 或已登记项目的精确打开；
- 从项目目录点选已登记项目；
- 启动恢复上次已登记项目；
- 桌面首次启动自动建立欢迎项目；
- 只读查看已登记正式版本。

### 3.2 B 类：已绑定外部原文件

再次打开首次导入时保留的外部原文件，或可由安全文件身份唯一证明是同一外部源的文件时，必须解析到既有 `projectId`，显示 §6 的关联确认。

这一分支：

- 不调用 `importExternal`；
- 不分配新 `projectId`、项目目录或 V1；
- 不显示“成功导入后删除原文件”复选框；
- 不用内容 Hash 在其他路径中搜索“相同项目”；
- 不在用户选择动作前切换或覆盖当前画布。

### 3.3 C 类：真正全新的外部 HTML

一份 HTML 既不是有效项目文件，也没有任何外部源关联时，才进入 §5 的首次导入确认。

项目目录里未登记的额外 HTML、未登记的项目副本、v4 以前且无法安全恢复的项目文件，也属于 C 类；它们不能仅凭目录形态或相同内容继承一个项目身份。

### 3.4 纯浏览器预览

纯浏览器预览不建立本地项目、外部源关联或删除权限，不进入本文导入流程。

## 4. 外部源关联

### 4.1 它是什么，不是什么

外部源关联是 Registry 持久保存的一条查找关系：

```text
经过主进程验证的外部源身份 → 唯一 projectId
```

它用于回答“用户再次从原来的地方打开这份文件时，应该回到哪个 PageRoot 项目”。它不是项目身份本身；项目身份仍是 Registry 中登记根目录约束下的 `projectId`、`documentId` 和受管文件身份。

它也不是内容去重：

- 两个不同路径的文件即使 Hash 完全相同，也不会因此自动归为同一项目；
- 不能扫描所有项目的 V1 Hash 后猜测用户想打开哪一个；
- Hash 只用于证明内容是否仍与首次导入一致，以及防止确认期间内容竞态。

### 4.2 同一外部源的判定

主进程在首次导入前记录经过规范化和真实路径校验的外部源键，并记录当时内容 Hash。实现可以同时保存安全的操作系统文件身份，用于处理同一路径的别名或可唯一证明的移动，但必须遵守：

1. 原路径再次打开时能稳定找到原项目；
2. 路径键、文件身份都只能由主进程/Repository 计算，Renderer 不能自报；
3. 文件身份发生变化但规范化路径相同时，先按“已绑定源内容已变化”安全处理，不自动建第二个项目；
4. 只有 Hash 相同、路径/文件身份不同，不能建立关联；
5. 软链接逃逸、不可读目标、非普通文件失败关闭。

### 4.3 生命周期

外部源关联在首次导入事务中与项目登记一起发布。只有项目已经完整可打开，关联才可见；失败导入不能留下悬空关联。

关联不因以下行为消失：

- 用户编辑 `A-V1.html`；
- 当前本地编辑与 V1 不同；
- 用户采纳 V2、V3；
- 用户切到历史版本查看或继续编辑；
- 外部原文件被用户选择移入废纸篓；
- 应用退出或升级。

如果原文件后来从废纸篓恢复到受绑定路径，再次打开仍回到原项目。

### 4.4 唯一性与并发

必须在 Repository/Registry 权威层实现以下硬约束，不能只靠界面禁用按钮：

- 一个外部源键最多有一个已提交的 `projectId`；
- 同一源的并发首次导入请求只能有一个成功发布，后到请求重新解析为 B 类；
- `pendingImports` 与已提交关联共同参与冲突检查，崩溃恢复不能各自发布第二个项目；
- 关联写入、项目发布和恢复保持可重试、幂等；
- 项目已经编辑或晋升后，仍然能通过关联返回该项目，不能把“项目仍是刚导入且 V1 未修改”作为能否关联的前提。

现有 `importSourceKey + importSourceSha256` 的导入重试语义不足以承担长期关联：当 V1 工作文件已修改、已晋升到更高版本或当前活动 Working Copy 改变时，关联仍必须成立。实施不得继续把“可恢复一次导入重试”等同于“这份外部源永久属于哪个项目”。

### 4.5 不提供“多个项目歧义选择器”

本需求不设计“历史上同一外部源已关联多个项目，让用户选择保留哪个”的产品流程，也不自动删除、合并或猜测任何项目。

上线前的数据迁移只能在现有 Registry 证据唯一时补建关联，不能按文件名或 Hash 猜测。若开发/测试历史数据已经人为制造同一源的重复声明，迁移与诊断工具必须在不删除项目的前提下阻止继续产生新声明，并在发布门禁前完成修复。正常用户界面不出现多项目选择框。

若运行时仍检测到违反唯一性的损坏状态，产品失败关闭：保持当前项目和所有磁盘文件不变，显示可诊断错误，不自动导入第三个项目。这是完整性故障，不是正常用户分支。

## 5. 首次导入确认

### 5.1 固定文案

真正全新的外部 HTML 使用：

```text
要把「产品首页.html」导入 PageRoot 吗？
会在「文稿 › PageRoot › 项目」里创建新项目，可见文件保存为 产品首页-V1.html。
初始版本 V1 与你这次选择的文件完全一致。之后的修改会自动保存在项目内文件，不会回写这份原文件。
后续只有在你采纳 AI 修改后，才会创建 -V2、-V3。
同目录的图片等资源不会一起导入。

☐ 成功导入后删除原文件

［取消］［导入并打开］
```

替换规则：

| 位置 | 规则 | 例子 |
|---|---|---|
| 「产品首页.html」 | 用户选中文件的当前主文件名，含扩展名，不含目录 | `报告.htm` → 「报告.htm」 |
| 文稿 › PageRoot › 项目 | 默认项目根的用户可见面包屑；非默认根按实际用户可见路径显示 | `~/Documents/PageRoot/项目` → 文稿 › PageRoot › 项目 |
| 产品首页-V1.html | 必须与 Repository 实际命名函数一致 | `报告.htm` → `报告-V1.htm` |

不显示尚未分配的具体项目文件夹名。同名碰撞可能让真实目录成为 `产品首页 (2)`，确认框不提前占用或承诺该目录名。

### 5.2 控件

| 控件 | 规则 |
|---|---|
| “成功导入后删除原文件” | 每次打开都默认未勾选；切换待确认文件后恢复未勾选；不写入偏好、Registry 或项目记录 |
| 取消 / Escape / 点按遮罩 | 不导入、不删除、不切换当前项目 |
| 导入并打开 | 主按钮；先完成 §7 的安全切换边界，再执行导入 |
| Enter | 激活主按钮 |

视觉复用应用内确认框，不为冷启动、Finder 双击、Dock 或文件菜单建立不同文案。

### 5.3 确认前不得做的事

出现确认框前只允许验证路径、扩展名、可读性，完成 §3 分类，并用纯函数计算展示名。禁止：

- 调用 `importExternal`；
- 写入 Registry、`pendingImports`、Recent 或当前活动文件；
- 创建项目文件夹或 staging 目录；
- 把外部 HTML 发布到 `DocumentSession` 或编辑画布；
- 删除、移动或改名原稿。

## 6. 再次打开已导入原文件

### 6.1 确认框要展示的事实

外部源已经关联项目时，使用独立于首次导入的确认框：

```text
「产品首页.html」已经导入 PageRoot
这份原文件已关联到项目「产品首页」。

当前本地编辑：基于版本 6 · 有已保存修改
最新正式版本：版本 6
初始版本 V1：与首次导入时所选文件一致
当前这份原文件与项目初始版本 V1 完全一致。

［取消］［查看初始版本 V1］［继续当前项目］
```

如果当前本地编辑与基线一致，第一行改为：

```text
当前本地编辑：基于版本 6 · 与该版本一致
```

如果当前本地编辑基于 V2、最新正式版本已经是 V6，两行必须分别显示真实值，不能合并成一句“最新版本 V6”。这正是“最新正式 Version”和“当前本地编辑”不能混用的原因。

如果外部原文件当前 Hash 已经与首次导入 Hash 不同，最后两行改为：

```text
初始版本 V1：与首次导入时所选文件一致
当前这份原文件在首次导入后发生了变化；继续不会把这些变化自动导入或覆盖项目内容。
```

### 6.2 “继续当前项目”打开什么

“继续当前项目”是主操作，打开该项目当前活动的可编辑本地工作稿：

- 它可能基于最新正式版本，也可能基于用户之前选择的某个历史版本；
- 它可能与所基于的正式版本完全一致，也可能包含已经自动保存但尚未形成新正式版本的本地修改；
- 它不是外部原稿；
- 它不是只读的“最新正式版本快照”。

因此按钮不得写成“打开项目最新版本”。“最新正式版本”只是项目事实之一，不必然等于用户上次正在编辑的内容。

### 6.3 “查看初始版本 V1”打开什么

“查看初始版本 V1”打开首次导入快照的只读视图。这个 V1 永远与首次导入时所选文件一致，不受后来本地编辑影响。

进入只读 V1 后，沿用版本历史中的“基于此版本继续编辑”。现行合同是**每个 Version 最多复用一个既有 Working Copy**：

- 如果基于 V1 的本地工作稿没有后续修改，继续编辑时看到的内容等于干净 V1；
- 如果用户以前已经基于 V1 做过本地修改，继续编辑会回到那份既有本地工作稿，界面必须先说明“将继续之前基于 V1 的本地编辑”，不能声称“从原始 V1 重新开始”；
- 只读 V1 快照本身始终不变。

如果未来要支持“保留既有 V1 本地修改，同时再创建一条全新的干净 V1 编辑分支”，需要把“一 Version 一 Working Copy”升级为多分支模型，或引入显式归档/重置事务。该能力不属于本文，不能借这次打开逻辑暗中实现。

### 6.4 取消

取消、Escape、点按遮罩均保持当前项目和画布不变，不更新 Recent，不改变外部源关联，也不自动打开外部原文件。

## 7. 当前项目切换与“正在确认当前画布”

打开请求和画布安全保存是相关但不同的状态：

- §3 的文件分类是 Repository 只读判断；
- 用户在 §5 或 §6 作出会切换项目/视图的选择后，`ProjectWorkflow` 才收口当前编辑、评论、附件和画布 generation；
- 当前画布收口成功后，才能发布新项目/新视图；失败则保留旧项目并明确报错。

状态顺序固定为：

```text
收到打开请求
  → 只读分类
  → 等待用户选择
  → 收口当前项目与当前 Canvas generation
  → 导入新项目 / 打开已有项目 / 打开只读 V1
  → 新画布用同一 source Hash 回报 ACK
  → 成功，显示“已安全保存”或“历史版本 · 只读”
```

“正在确认当前画布…”只能表示一个真实、尚未结束的 Canvas generation/Hash 收口过程，不能作为任何未知状态的兜底文案。每个进入该状态的操作必须：

1. 绑定唯一 `operationId + projectId + sourcePath + sourceSha256 + canvasGeneration`；
2. 忽略旧项目、旧 Hash 或旧 generation 的迟到 ACK；
3. 在成功、取消、替换、失败、渲染器销毁和应用退出路径释放 pending 状态；
4. 无法完成时给出明确失败和重试入口，恢复到仍可操作的旧项目；
5. 禁止无限显示“正在确认当前画布…”。具体超时值由技术计划统一定义并由 Electron 测试锁定。

仅仅完成“同一原文件回到已有项目”不能替代画布 ACK 修复；反过来，只修 ACK 也不能解决重复项目。两条都必须通过验收。

## 8. 首次导入并打开事务

用户点击“导入并打开”后，顺序固定为：

```text
收口当前项目和当前画布
  → 再次读取外部 HTML，校验未被确认期间修改
  → 预占唯一外部源关联和 pending import
  → 按现行 v4 原子导入事务发布项目根、隐藏 V1、可见 V1 工作文件和 Registry
  → 把外部源关联提交为该 projectId
  → 当前目标切换到项目内 V1 工作文件并等待新画布 ACK
  → 若勾选删除：仅把刚才那份外部 HTML 移入废纸篓
  → 显示成功结果
```

任一步失败不得宣布导入成功，也不得留下已注册但不可打开的项目或悬空外部源关联。确认期间文件 Hash 改变时，导入失败，原稿和当前项目保持不变，提示“文件在确认期间被修改，没有导入”。

并发中若另一个请求已经成功绑定同一外部源，本请求不再导入；重新分类为 B 类并展示既有项目事实。

## 9. 成功导入后删除原文件

### 9.1 产品含义

默认不删除。只有用户在首次导入确认中勾选，并且新 v4 项目和外部源关联已经完整发布、当前目标已经切到 V1 工作文件后，才把原位置上的那一份 HTML 移入 macOS 废纸篓。

这不是把原稿 `mv` 成 V1。V1 工作文件始终是在项目目录内新发布的副本；同目录图片、CSS、JS 和其他文件一律不动。

### 9.2 删除权限

只允许删除同时满足以下条件的对象：

1. 本轮首次导入请求中由主进程验证的绝对路径；
2. 导入已成功，且删除前重读 Hash 仍等于本轮导入 Hash；
3. 普通文件，不是目录或软链接；
4. 真实路径不在配置项目根内，也不是新 V1、隐藏快照或任何项目文件。

Renderer 只提交本轮不透明请求 ID 和用户是否勾选，不能提交任意待删除路径。

### 9.3 删除失败与崩溃

删除失败不回滚已经发布的项目和外部源关联。提示：

> 项目已导入。原文件未能删除，仍留在原来的位置。

进程若在项目发布后、删除完成前崩溃，项目和关联都已经存在，原稿可能仍在。下次打开该原稿必须进入 B 类“已经导入”确认，不能再次出现首次导入框或创建另一个项目。

## 10. 成功提示

| 结果 | 提示 |
|---|---|
| 导入成功，未勾选删除 | 标题“已导入 PageRoot”；正文“初始版本 V1 已保存为 `<V1 文件名>`，与刚才选择的文件一致。原文件没有改动。” |
| 导入成功，原稿已进废纸篓 | 标题“已导入 PageRoot”；正文“初始版本 V1 已保存为 `<V1 文件名>`。原文件已移入废纸篓。” |
| 导入成功，删除失败 | 标题“已导入 PageRoot”；正文使用 §9.3 |
| 再次打开并继续当前项目 | 不显示“再次导入成功”；打开完成后显示项目当前保存/版本状态 |
| 再次打开并查看 V1 | 显示“初始版本 V1 · 只读” |

首次导入成功提示提供“在文件夹中打开”，定位项目的用户可见根目录，不是外部原稿目录或 `.pageroot/`。

现行“已打开 / 原来的文件没有改动”在实施后废止，因为它既没有说明新项目位置，也无法覆盖再次打开已有源的语义。

## 11. 打开队列与并发请求

所有入口共用同一个分类器、队列和两种确认框：文件菜单、标题栏“+”、Finder 双击、系统“打开方式”、Dock、命令行和冷启动 handoff。

- 确认框可见时，更新的外部请求可以替换待确认文件；旧请求必须明确取消，不能在后台继续导入或打开。
- 被替换后，首次导入删除复选框恢复未勾选；两种确认框根据新文件的 A/B/C 分类重新选择。
- 较慢的旧读取、旧 Registry 查询、旧画布 ACK 不能在用户已确认 B 后再发布 A。
- 同一源同时从两个入口送达时，只能复用一个 pending/committed 关联。
- 无效路径、非 HTML、文件消失或完整性校验失败只报告失败，不改变当前项目。
- 进程退出时，未确认请求视为取消；close-commit handoff 只保存已验证路径，不保存用户同意、删除勾选或项目切换完成状态。下次启动重新分类。

## 12. 状态与权限所有权

| 事实 | 唯一 owner | 是否持久 |
|---|---|---|
| 已验证外部路径、请求 ID、路径键、当前 Hash | 主进程打开队列 / Repository | 请求期内存；路径关联提交后才持久 |
| A/B/C 分类结果 | Repository | 本次请求快照，不由 Renderer 推断 |
| 外部源 → projectId 关联、初始导入 Hash | Registry | 是 |
| 确认框类型、是否可见、删除勾选 | `ProjectWorkflow` 编排的渲染器投影 | 否 |
| 项目身份、版本、工作文件和当前活动 Working Copy | `ProjectFileRepository` + Registry + 项目 manifest/runtime | 是 |
| `viewingVersionId` | 现有 `VersionSession` | 按现有合同 |
| 当前 Canvas generation/Hash ACK | 现有画布会话 owner | 仅当前画布生命周期 |
| 是否把原稿移入废纸篓 | 主进程一次性特权操作 | 只持久结果，不持久用户偏好 |

Workbench 只能投影这些状态并发送用户意图，不能再维护一套平行的“是否已经导入”“关联项目”“当前版本”或画布确认布尔值。

## 13. 外部原文件后来发生变化

已绑定路径上的外部 HTML 后来发生变化时，PageRoot 仍将其识别为 B 类关联源，但不得：

- 自动把变化覆盖到当前项目；
- 自动重写 V1；
- 自动创建新项目；
- 自动把外部变化合并到当前工作文件；
- 继续声称当前外部文件与 V1 完全一致。

用户仍可“继续当前项目”或“查看初始版本 V1”。如何显式比较、导入或协调外部原文件的新内容属于后续独立需求；本文不建立隐式同步关系。

如果同一路径后来被完全无关的新文件占用，产品仍优先保护既有唯一关联并提示内容已变化。未来如需“解除旧关联并把该路径作为新项目导入”，必须是明确、可审计且不删除旧项目的独立流程，不能由本次需求自动猜测。

## 14. 工程影响与范围边界

这不是只改一个弹窗，但也不要求重写版本系统。

必须改动的产品/技术面：

1. Registry/Repository：把导入重试证据升级为持久外部源关联，并加入唯一性、并发和恢复约束；
2. 打开分类：`resolveOpenTarget` 之外增加明确的 A/B/C 结果，不能再用 `null = 一律新导入`；
3. Bridge/IPC：只传不透明请求和已验证分类所需事实，不扩大任意路径读取/删除权限；
4. `ProjectWorkflow`/UI：新增“已经导入”确认及版本状态投影，统一取消、替换和终态清理；
5. Canvas 状态：补齐 generation/Hash ACK 的成功、失败、迟到和销毁收口，消除无限 pending；
6. 迁移与测试：唯一证据回填、并发导入、崩溃恢复、外部源已变化、历史 V1 查看和真实 Electron 打开链路。

明确不改：

- 正式版本仍只有首次 V1 和显式 Candidate 采纳；
- 一 Version 一 Working Copy 的现行模型不变；
- 不增加“干净 V1 新分支”；
- 不做 Hash 去重、项目合并或用户歧义选择器；
- 不导入外部同目录资源；
- 不把外部原稿变成持续双向同步文件；
- 不改变 Candidate、Promotion 和项目根写权限合同。

预计这是一次**中等规模的纵向改动**：风险主要在 Registry 迁移/唯一性和打开状态机，不在版本模型。实施应保持 1–2 个完整 PR；只有硬性迁移阻塞时才扩到第 3 个。不能按 Repository、Bridge、UI 各拆一个长期互相不完整的 PR。

## 15. 失败与恢复

| 情况 | 用户看到 | 磁盘与状态 |
|---|---|---|
| 文件选择器取消 | 无新提示 | 不变 |
| 首次导入确认取消 | 继续当前项目 | 不创建项目、不建关联、不删除 |
| 已导入确认取消 | 继续当前项目 | 关联不变 |
| 确认期间新文件内容被改 | 本次操作失败，可重新打开 | 原稿和当前项目不变 |
| 导入事务失败 | 明确导入失败 | 不留半截项目或悬空关联 |
| 并发请求抢先完成同源导入 | 转为“已经导入”确认 | 只有一个项目和一个关联 |
| 原稿保留后再次打开 | 显示 §6，不是首次导入框 | 不创建第二个项目 |
| 原稿内容后来变化 | 显示差异说明 | 不覆盖、不合并、不新建项目 |
| 删除失败 | 项目已导入、原稿仍在 | 项目与关联保留 |
| 导入成功后、删除前崩溃 | 重启后可打开项目；再次打开原稿进入 §6 | 项目和关联已在，原稿可能仍在 |
| 当前画布收口失败或超时 | 明确失败与重试，不无限 pending | 保持原项目可操作，不发布新目标 |
| Registry 唯一性损坏 | 完整性错误，不给项目选择器 | 保留所有项目，不继续导入 |

## 16. 验收标准

### 16.1 文件与版本语义

- [ ] 首次导入后，隐藏 V1 快照、可见 `…-V1.html` 和导入时外部原文件三者字节完全一致。
- [ ] 本地编辑自动保存到项目内可见工作文件，不改外部原稿和隐藏 V1。
- [ ] 连续本地保存不创建新正式版本；第一次明确采纳 AI Candidate 才创建 V2。
- [ ] UI 不生成或展示 `A-working-copy.html`，也不要求用户理解 Working Copy 术语。
- [ ] 所有 V1 文案均区分“与首次导入时一致”和“当前外部文件仍与 V1 一致”。

### 16.2 首次导入

- [ ] 打开真正未绑定 HTML 时出现 §5 确认框；确认前不创建项目、不写 Registry/Recent、不切画布。
- [ ] 确认框 V1 文件名与随后磁盘上的可见文件完全一致。
- [ ] 取消、Escape、点按遮罩都不导入、不删除，当前项目保持不变。
- [ ] 默认不删除原稿；勾选后只在项目和关联完整发布后移入废纸篓。
- [ ] 导入成功原子地产生一个项目、一份 V1 和一条唯一外部源关联。

### 16.3 再次打开同一原文件

- [ ] 保留原稿并再次打开时显示 §6“已经导入”确认，不显示首次导入确认。
- [ ] 再次打开前后 Registry 只有原 `projectId`，项目目录数和正式版本数均不增加。
- [ ] “继续当前项目”打开现有可编辑工作稿，保留当前 `currentBasedOnVersionId` 和已保存本地修改。
- [ ] 对话框分别显示当前本地编辑基于的版本与最新正式版本；两者不同时不互相覆盖。
- [ ] “查看初始版本 V1”打开不可变 V1 只读视图，不覆盖当前本地工作稿。
- [ ] 从 V1 继续编辑时复用既有 V1 Working Copy；若它已有修改，先明确告知，不伪装成干净 V1。
- [ ] 外部原文件 Hash 已变化时提示变化，不导入、不覆盖、不创建第二个项目。
- [ ] 同内容的另一路径仍按新外部文件处理，证明没有 Hash 去重。

### 16.4 唯一性、队列与恢复

- [ ] 同一外部源的两个并发导入只有一个项目成功，另一个重新解析为已绑定源。
- [ ] 导入成功后无论 V1 工作文件已修改、已晋升 V2+ 或活动 Working Copy 已切换，再次打开原稿仍回到同一项目。
- [ ] `pendingImports` 崩溃恢复不会发布第二个项目或第二条声明。
- [ ] Renderer 不能自造外部源键、`projectId` 或删除路径。
- [ ] 新打开请求替换旧确认时，旧请求、旧读取和旧 Canvas ACK 都不能迟到发布。
- [ ] 任何“正在确认当前画布…”状态都能在成功、取消、失败、替换、销毁或超时后退出。
- [ ] 真实 Electron 测试覆盖 Finder/`open-file` 冷启动和运行中打开，而不只覆盖 Repository 单测。
- [ ] 不存在面向用户的多个关联项目选择器；唯一性损坏失败关闭且不改磁盘。
