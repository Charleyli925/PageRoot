# Stemmio Design Review Protocol

状态：V1。设计原则见 [PRODUCT_DESIGN_SYSTEM](PRODUCT_DESIGN_SYSTEM.md)，视觉取证方法见
[DESIGN_LANGUAGE §5](DESIGN_LANGUAGE.md#5-ui-修改标准流程design-qa)。本协议定义如何形成可复核结论。

## 选择任务模式

| 模式 | 输入 / 适用情形 | 最小输出 |
| --- | --- | --- |
| SCREEN REVIEW | 当前屏幕、截图、布局或层级问题 | 视觉依据、可证明的问题、局部建议、证据限制 |
| FLOW AUDIT | 多步骤任务或重新进入体验 | 流程图或步骤表、状态矩阵、阻断点与恢复路径 |
| DESIGN CHANGE | 已授权修改布局、文案、状态或交互 | 相关合同、验收条件、实现后的对应证据 |
| CODE REVIEW | UI diff 或源码审查 | 精确 file:line、触发条件、实际影响；未运行行为明确标记 |
| AI EXPERIENCE LENS | 上述任一模式涉及 Agent、Candidate、Review、采纳 | 意图、进展、检查点、结果、控制权和恢复补充检查 |

纯内部重构且没有用户可见影响不触发设计流程。单处文案或令牌调整按 DESIGN_LANGUAGE 的轻量例外执行，
不强制完整审计、截图或新测试。只读请求保持只读；发现问题不自动授权修复。

## 取证与流程覆盖

先记录任务、起止点、产品版本 / commit、运行环境、合成数据、相关合同和证据类型。
截图审阅只判断可见事实；源码能证明分支与状态来源，不能证明真实焦点、IME、布局或流程已经通过。
历史截图与 QA 仅作为带日期的历史证据，不能冒充当前版本。
真实交互审计先采集当前截图，再操作并记录关键前后状态；仅使用隔离合成项目，不改用户项目。

从用户目标映射 Happy Path，再检查适用的 alternate、error、loading、empty、re-entry、
back/forward 和 recovery。桌面没有 URL 历史时检查真实返回/标签切换；不发明浏览器导航要求。
AI 输出 fixture 可以验证应用闭环，不能证明真实厂商认证、生成质量或协议验收。

每行使用以下结构；不能用缺少证据的“通过”填满矩阵：

| 步骤 / 状态 | 用户意图与对象 | 可用动作 / 反馈 | 结果 / 下一步 / 恢复 | 证据 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 按本次任务填写 | Project / File / Version | 真实状态与操作 | 按对应合同 | 截图、trace 或 file:line | 通过 / 失败 / 未验证 / 不适用（说明原因） |

异步操作额外核对：等待时是否保留上下文、重复点击是否重复执行、取消请求是否冒充已停止、
切换后迟到结果是否写到新对象、重新进入能否恢复同一操作、失败后是否保留已有结果。
视觉实现按需检查语义 button/link、键盘操作与 focus-visible、表单标签和就近错误、
异步反馈、窄窗口/缩放、对比度与非颜色线索、reduced motion、危险动作的确认时机。
确认遵循现有授权合同，不为普通可逆操作新增弹窗。

## Issue Vocabulary

类别 ID 稳定；实例使用 `SD-001` 等审计内编号，并记录类别。一个根因对应一个实例，可有次级类别。

| 类别 ID | 可观察的问题 |
| --- | --- |
| CONTEXT-LOSS | 项目、文件、版本或当前位置在切换后丢失 / 混淆 |
| STATE-AMBIGUITY | 无法区分运行、等待、成功、失败或停止未确认 |
| RESULT-UNCLEAR | 操作结束后不清楚产生了什么，或展示与结果事实不符 |
| NEXT-ACTION-MISSING | 任务需要继续，但缺少可发现的下一步 |
| RECOVERY-DEAD-END | 失败后缺少合同允许的恢复出口 |
| VERSION-SCOPE-AMBIGUITY | 操作对象或版本基础含混，可能作用于错误版本 |
| AGENT-INTENT-HIDDEN | 用户无法辨别 AI 本轮任务或作用范围 |
| AGENT-PROGRESS-OPAQUE | 真实阶段不可辨，或展示伪造的进度 / 完成 |
| APPROVAL-MISPLACED | 危险动作确认缺失、太晚，或可逆操作被无必要确认阻断 |
| HIERARCHY-COLLISION | 多个动作争夺主层级或重复决定造成歧义 |
| ACCESSIBILITY-BARRIER | 键盘、焦点、标签、对比度或降级妨碍任务完成 |
| CONTRACT-CONFLICT | 同一设计决策的活动文档存在矛盾；不是已证实运行时缺陷 |

不为了套词汇制造发现。新类别只在现有类别无法表达重复问题时新增；历史实例保持原 ID。

## 严重性、置信度与发现格式

- P0：严重数据损坏、安全/隐私越界等紧急影响。
- P1：错误文件/版本写入、来源不可追溯、关键任务无法完成或必需确定性门禁失败。
- P2：存在可用路径但理解、效率或一致性明显受损；记录后续，不扩大已通过的任务范围。
- P3：非阻断视觉或文案打磨。

严重性按真实影响，不由类别或评论标签决定。尚未证实影响的项标为“待核实”，不假定 P1。
Confidence 独立标注：高（当前直接重现或确定性源码证据）、中（局部证据支持，关键状态未观察）、
低（推测，只进入待验证项）。截图对外观可以高置信，对未操作的交互仍是未验证。

每条发现记录：实例 ID / 类别、Severity / Confidence、用户目标、触发步骤、预期与实际、
影响、精确证据位置及其版本、最小建议、可观测验收条件。代码结论使用 `file:line`；
图片使用路径与状态，动态问题附步骤或 trace。不要只写“更高级”“不直观”或设计定律名称。

验收条件写成：给定哪个项目/版本与状态 → 用户执行什么 → 可观察结果是什么 → 哪些既有内容应保留。
例如：Candidate 就绪后进入审阅，当前源保持不变；明确采纳后标题、版本与打开内容一致；
拒绝或失败路径保留合同规定的原内容与可用恢复动作。各项分别提供证据。

## 完成与记录

输出先给结论，再给关键发现、状态覆盖和未验证项。没有可证明的问题可以报告“未发现”，
但必须限定证据范围；未执行、跳过、未知、失败和通过分开记录。
审计完成表示约定范围已检查并记录缺口，不表示产品所有路径通过；完整链路验收必须具备对应运行证据。

修改任务使用 [测试策略](../tests/TEST_STRATEGY.md) 的 gate:plan / gate:edit / task:finish，
不另造门禁，也不把静态审查当 Electron 验收。按 [AGENTS](../AGENTS.md) 的范围停止规则处理 P2/P3。
视觉/交互 QA 追加 [design-qa](../design-qa.md)，如实写 passed / partial / blocked 及未验收边界；
不覆盖历史，也不为满足格式无条件写 passed。截图与完整运行日志保留在 output/design-qa/ 或既有测试报告目录，
不提交个人截图、真实项目数据或绝对个人路径。
