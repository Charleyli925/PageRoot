# ADR-0041: Stage Codex through direct App Server preflight

> Status: Accepted
> Date: 2026-08-26

## Context

Stemmio keeps the right sidebar and durable Conversation records as an Agent
conversation product. Execution progress, Agent-visible messages and Candidate
decisions continue to appear in that conversation flow so later capabilities,
including Skills, can extend the same product structure.

Pure Discussion turns are retired. A user message can currently start only a
page-comment modification; it cannot ask either Qoder or Codex for a read-only
answer. Retiring Discussion does not authorize replacing the conversation UI or
data model with a delivery form. Any such redesign requires a separate product
decision.

The earlier Codex plan placed `codex-acp` between Stemmio and Codex App Server.
With Discussion removed, that adapter adds another protocol, process and version
boundary without providing Candidate authority or the agent-native write sandbox.
The provider-neutral registry already supports a runtime other than ACP.

## Decision

- Codex uses the official Codex App Server v2 JSONL protocol directly through a
  runtime identified as `app-server`.
- `@openai/codex` is exact-pinned. npm integrity, package/runtime identity and
  the Schema generated by that exact binary are reviewed together and fail
  closed on drift.
- Preflight performs `initialize`, `account/read` and paginated `model/list`.
  It does not start a thread or turn, log in, open a browser, create a Request,
  or persist account details.
- Public model ids are provider-namespaced and reasoning choices come only from
  the live catalog.
- Raw stderr, account email, tokens and login URLs never cross the provider
  boundary. `APP_SERVER_LOGS` is removed from the child environment.
- Apps, plugins, Browser, Computer Use and multi-agent features are disabled for
  the probe process.
- PR3 does not register Codex in the default provider catalog. Its provider
  advertises `execution: false`, and its execution-policy/launch methods fail
  closed. Qoder remains the only product-visible provider.

## Trusted-local-Agent boundary

The pinned Codex sandbox was tested with an Attempt-shaped workspace. It permits
the unique output root and rejects writes to frozen input, control evidence,
unrelated paths and `/tmp`. Its current public Schema does not restrict general
read roots, so Codex remains a user-enabled trusted local Agent and the product
must disclose that it may read local files while modifying.

This decision does not weaken Candidate authority: a later Execution stage must
still allow only the unique Candidate output, run the fixed Bridge finalizer,
enter Review, and require explicit adoption. No Agent message, App Server
`turn/completed` notification or process exit can publish a Candidate.

## Consequences

- PR4 may register Codex only behind the independent `codexExecution` hard gate.
- Each modification uses a fresh ephemeral App Server thread. Provider thread
  ids remain disposable bindings, not Conversation or Candidate authority.
- Permission requests are denied; no permission UI, Discussion resume or hidden
  provider-session continuity is required for the first modification release.
- Packaging and installed-app proof remain a later independent gate.
